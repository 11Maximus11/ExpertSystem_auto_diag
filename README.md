# AutoDiag Pro AI — Экспертная ИИ-система автодиагностики и пошагового ремонта (Django + AirLLM Qwen3.5 + Adaptive GPU VRAM + RayNeo AR HUD)

**AutoDiag Pro AI** — полнофункциональная кроссплатформенная экспертная система для автомастерских, диагностов и автовладельцев, выполняющая комплексную диагностику неисправностей автомобилей по описанию симптомов, кодам ошибок OBD-II (DTC), логам сканеров, голосовым запросам и фотографиям узлов/приборной панели с выдачей пошаговых интерактивных инструкций по ремонту.

Система полностью автономна (**без зависимости от Ollama или внешних серверов `llama-server`**) и работает напрямую через официальный послойный движок **[AirLLM](https://github.com/lyogavin/airllm)** (`AirLLMQwen3_5`) с современной мультимодальной моделью **`Qwen/Qwen3.5-4B`** (`Qwen3_5ForConditionalGeneration`), автоматической предзагрузкой в видеопамять GPU при старте сервиса и расширенным окном контекста (`6144` токена).

## 1. Инструкция по скачиванию модели и запуску проекта (Быстрый старт)

> **Важно:** В репозиторий Git веса нейросети (~8.1 ГБ) не загружаются. Перед первым запуском (или автоматически во время первого старта) модель **`Qwen/Qwen3.5-4B`** скачивается из HuggingFace и нарезается на 35 послойных шардов AirLLM с помощью скрипта `prepare_airllm_model.py`.

### Способ А. Запуск в одну команду на Windows (PowerShell)
Скрипт `run_dev.ps1` сам создаст `.venv` (если его еще нет), установит PyTorch с поддержкой GPU CUDA + ядра `triton-windows` и `flash-linear-attention`, скачает и нарежет модель `Qwen/Qwen3.5-4B`, применит миграции БД и запустит сервер с автоматической предзагрузкой модели в видеопамять:

```powershell
.\run_dev.ps1
```

### Способ Б. Пошаговая ручная установка и запуск на Windows (PowerShell)
Если вы настраиваете окружение вручную с нуля:

```powershell
# 1. Создайте виртуальное окружение в корне проекта
python -m venv .venv

# 2. Обновите pip и установите PyTorch с поддержкой GPU (CUDA 12.4)
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu124

# 3. Установите ускоренные ядра Gated DeltaNet для Qwen3.5 на Windows
.\.venv\Scripts\python.exe -m pip install triton-windows flash-linear-attention

# 4. Установите остальные зависимости проекта (Django, AirLLM, Pydantic, Whisper и др.)
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# 5. Скачайте модель Qwen/Qwen3.5-4B с HuggingFace и нарежьте её на шарды AirLLM (~8.1 ГБ)
.\.venv\Scripts\python.exe prepare_airllm_model.py

# 6. Примените миграции базы данных SQLite
.\.venv\Scripts\python.exe manage.py migrate

# 7. Запустите сервер (модель автоматически предзагрузится в видеопамять GPU при старте!)
.\.venv\Scripts\python.exe manage.py runserver 0.0.0.0:8000 --noreload
```

### Способ В. Быстрый запуск на Linux (Bash)

## 2. Подробно о скачивании и послойной нарезке модели AirLLM

Для работы послойного движка **AirLLM (`AirLLMQwen3_5`)** требуется:
1. Папка конфигурации, токенизатора и визуального процессора: `models/Qwen3.5-4B/`
2. Папка с 35 послойными шардами весов (`.safetensors`): `models/airllm_shards/splitted_model/`

### Как скачать и подготовить модель:
Выполните скрипт подготовки:
```powershell
.\.venv\Scripts\python.exe prepare_airllm_model.py
```

**Что делает `prepare_airllm_model.py`:**
1. Проверяет, есть ли уже готовые 35 шардов в `models/airllm_shards/splitted_model/`. Если все шарды и маркеры `.safetensors.done` на месте — скрипт завершается мгновенно (`0.1 сек`).
2. Если шардов еще нет — через `huggingface_hub.snapshot_download` скачивает официальный репозиторий **[`Qwen/Qwen3.5-4B`](https://huggingface.co/Qwen/Qwen3.5-4B)** (~8.1 ГБ в `bfloat16`) в локальную относительную папку `models/Qwen3.5-4B/`.
3. За **один проход** (~60 секунд на SSD) читает исходные файлы весов и нарезает их на **35 независимых послойных шардов** в `models/airllm_shards/splitted_model/`:
   - `model.language_model.embed_tokens.safetensors` — входные эмбеддинги и привязанная голова `lm_head`
   - `model.language_model.layers.0.safetensors` ... `model.language_model.layers.31.safetensors` — 32 гибридных декодер-слоя (Gated DeltaNet + Gated Attention)
   - `model.language_model.norm.safetensors` — финальная нормализация
   - `model.visual.safetensors` — мультимодальный визуальный энкодер SigLIP для анализа фото поломок и приборной панели
4. Автоматически удаляет исходные монолитные файлы `model.safetensors-00001-of-00002.safetensors` после нарезки, чтобы **не дублировать занятое место на диске** (остаются только конфиги токенизатора/процессора в `models/Qwen3.5-4B/` и нарезанные шарды в `models/airllm_shards/splitted_model/`).

> **Примечание:** Даже если вы не запустили `prepare_airllm_model.py` вручную, при старте `manage.py runserver` оркестратор автоматически вызовет проверку и при необходимости скачает и нарежет модель сам.

### Как переключиться на более крупную модель (например, `Qwen/Qwen3.5-9B` или `Qwen/Qwen3.8-27B`)
Вся линейка моделей `Qwen3.5` / `Qwen3.8` нативно поддерживается классом `AirLLMQwen3_5`:
1. Укажите желаемый HuggingFace ID в переменной окружения `AIRLLM_MODEL_ID` (или в правой панели веб-интерфейса **«AirLLM & GPU» → «Модель AirLLM»**):
   ```powershell
   $env:AIRLLM_MODEL_ID = "Qwen/Qwen3.5-9B"
   ```
2. При необходимости включите 4-битную или 8-битную компрессию шардов (`AIRLLM_COMPRESSION=4bit` или `8bit` через `bitsandbytes`), чтобы на 8 ГБ видеопамяти в VRAM помещалось еще больше слоев тяжелой модели.

## 5. Автономный движок AirLLM (`AirLLMQwen3_5`), предзагрузка в VRAM и GPU-стриминг

В модуле [`diagnostics/airllm_vulkan_service.py`](file:///d:/GDrive/Документы/Visual%20Studio%202022/ExpertSystem_auto_diag/diagnostics/airllm_vulkan_service.py) реализован подкласс **`AdaptiveAirLLMQwen3_5(AirLLMQwen3_5)`**, который использует доступную видеопамять по максимуму независимо от объема VRAM (4 ГБ, 6 ГБ, 8 ГБ, 12 ГБ, 16 ГБ и более):

1. **Автоматическая предзагрузка в видеопамять при старте сервиса (`DiagnosticsConfig.ready`)**:
   - При запуске `manage.py runserver` (или `api_server.py`) система **сразу же предзагружает и прогревает модель в GPU VRAM** (~9.9 с на SSD), не дожидаясь первого сообщения от пользователя.
   - При необходимости предзагрузку можно отключить переменной окружения `AIRLLM_PRELOAD_ON_STARTUP=0`.
2. **Гарантированный резерв под расширенное окно контекста (`6144` токена)**:
   - Перед загрузкой весов система опрашивает реальную свободную видеопамять (`torch.cuda.mem_get_info(0)` и `vulkaninfo`) и резервирует неприкосновенный буфер под KV-кэш окна контекста (`max(1350 МБ, 19% общей VRAM)`).
3. **Закрепление максимума слоев в VRAM (Pinned GPU Layers)**:
   - Все слои, которые помещаются в оставшийся бюджет свободной видеопамяти (например, на RTX 3050 8 ГБ в VRAM постоянно закрепляются `embed_tokens`, `norm` и 24 из 32 слоев декодера — ~5.2 ГБ), загружаются напрямую на GPU (`cuda:0`) и **не перезагружаются с диска** при генерации каждого токена.
4. **Асинхронный PCIe DMA стриминг оставшихся слоев из Pinned RAM**:
   - Те слои, которые не поместились в бюджет VRAM (например, последние 8 слоев на 8 ГБ видеокарте), кэшируются в page-locked памяти хоста (`tensor.pin_memory()`) и копируются в GPU на лету через `non_blocking=True` в хуках AirLLM `_pre_hook` / `_post_hook` с немедленным освобождением буфера после прохода слоя.
5. **Ленивая подгрузка визуального энкодера (`model.visual`)**:
   - Мультимодальный энкодер `model.visual` (892 МБ) загружается в GPU только тогда, когда к запросу прикреплено фото или снимок с камеры, экономя почти 1 ГБ VRAM для текстовых слоев.

## 6. Фоновый воркер выжимки контекста и междиалоговая память (Zero-Wait Preemption)

Из-за ограниченного объема видеопамяти передавать всю длинную историю сообщений и объемные документы в каждый запрос неэффективно. В модуле [`diagnostics/context_worker.py`](file:///d:/GDrive/Документы/Visual%20Studio%202022/ExpertSystem_auto_diag/diagnostics/context_worker.py) реализован **вытесняемый фоновый воркер (`ContextSummarizerWorkerManager`)**:

1. **Фоновое сжатие после каждого сообщения**: как только пользователю выдан ответ, запускается фоновый поток, формирующий концентрированную техническую выжимку диалога (`DialogSession.summary`): марка/модель автомобиля, зафиксированные коды ошибок DTC, жалобы, установленные причины, а также какие шаги чеклиста и какие инструменты уже отмечены пользователем как выполненные.
2. **Междиалоговая память (`cross_dialog_memory_enabled`)**: при включении соответствующего переключателя в левой панели воркер также синхронизирует глобальную сводку **между всеми диалогами** (`SystemSettings.global_memory_summary`), позволяя ИИ помнить историю прошлых ремонтов и особенности машины в новых сессиях.
3. **Мгновенный принудительный сброс без ожидания (`preempt_if_running`)**:
   - Если пользователь задал новый вопрос, а фоновый воркер еще не успел завершить обновление выжимки после предыдущего сообщения — **система НЕ заставляет пользователя ждать**.
   - Вызов `context_worker_manager.preempt_if_running(session_id)` за `0 мс` выставляет событие отмены `cancel_event.set()` и инкрементирует поколение `worker_version`.
   - Старый воркер принудительно сбрасывается, система немедленно отвечает на новый вопрос (используя последнюю готовую выжимку), и только после ответа запускает новый фоновый воркер следующего поколения.

## 7. Строгий JSON-формат ответов, Function Calling и Optimistic UI

### Мгновенное отображение сообщения и анимация генерации (Optimistic UI)
- При нажатии «Отправить» сообщение пользователя (вместе с прикрепленными кодами ошибок DTC, превью фото и именами файлов) **мгновенно появляется в ленте чата**, не исчезая во время ожидания ответа.
- Сразу под сообщением пользователя отрисовывается анимированная карточка генерации ответа `AirLLM Qwen3.5-4B` с живым секундомером и подсветкой 4 этапов работы нейросети (прерывание воркера контекста → вызов инструментов БД DTC и RAG → послойная генерация через GPU VRAM + PCIe DMA → валидация JSON Schema).

### Строгий JSON-формат и инструменты (Function Calling)
В модуле [`diagnostics/schemas.py`](file:///d:/GDrive/Документы/Visual%20Studio%202022/ExpertSystem_auto_diag/diagnostics/schemas.py) все ответы модели приводятся к строго типизированной структуре **`DiagnosticStructuredResponse`** с использованием **Pydantic v2** и **JSON Schema (`jsonschema`)**:
- Поддерживаются как подробные диагностические ответы (`response_type="diagnostic"`, до `768` новых токенов), так и живое свободное общение (`response_type="general"`, до `450` новых токенов, без показа ложных карточек ошибок).
- Поддерживается автоматический вызов диагностических инструментов (**Function Calling**):
  - `lookup_dtc_code(code)` — точная карточка кода неисправности и эталонной телеметрии из базы данных.
  - `search_knowledge_base(symptom_query, system)` — гибридный RAG-поиск по `kb_data.json` и `VehicleDiagnosticSample.txt`.
  - `inspect_attached_image(filename, resolution)` — визуально-технический анализ прикрепленных фотографий и снимков с камеры через `Qwen3.5-VL` и CV-инспектор.
  - `build_repair_inventory(system, codes)` — формирование специфицированного перечня инструментов, запчастей и моментов затяжки.

## 8. Task-Friendly ответы: блок инвентаря и пошаговые чекбоксы задач

Каждый диагностический ответ экспертной системы визуализируется в виде удобной рабочей карты механика:
- **Карточки установленных неисправностей (`faults`)**: код ошибки, система, уровень критичности (`critical` / `warning`), шкала индекса здоровья узла (`Health Index %`) и первопричина.
- **Блок инвентаря (`inventory`)**: список необходимых инструментов, запчастей, расходников и средств защиты с указанием характеристик (размеры головок, моменты затяжки в Н·м, сопротивления в Ом) и **интерактивными чекбоксами наличия** (`Готово: X / Y`).
- **Пошаговый план ремонта (`repair_steps`)**: пронумерованные этапы работ с подробными инструкциями, эталонными параметрами, предупреждениями по технике безопасности и **интерактивными чекбоксами выполнения** (`Выполнено: X / Y`).
- Отметка любого чекбокса мгновенно сохраняется через API `/api/messages/<id>/toggle-task/`, синхронизируется между лентой диалога, правой панелью «Чеклист & Инвентарь» и окном AR-очков, а также передается фоновому воркеру контекста.

## 9. Мультимодальный ввод: словарь БД, камера, документы и голос

В нижней панели ввода (доступной под большим пальцем на мобильных устройствах) поддерживаются все виды ввода:
1. **Словарь кодов ошибок БД (`DTC`)**: объединяет `kb_data.json` и 32 733 строки телеметрии из `VehicleDiagnosticSample.txt`. Позволяет искать коды по номеру (`P0300`, `P0796`, `C0050`, `U1900`, `P0A80` и др.), фильтровать по системам и прикреплять к запросу в один клик.
2. **Встроенное окно камеры**: открывает видеопоток камеры прямо внутри веб-интерфейса (`getUserMedia`) с переключением фронтальной/тыльной камеры, координатной сеткой прицела и генератором тестового кадра приборной панели. Сделанный снимок напрямую передается в визуальный блок `Qwen3.5-4B` (`model.visual`).
3. **Прикрепление фото и документов**: загрузка изображений (`.jpg`, `.png`, `.webp`) и технических файлов/логов сканеров (`.txt`, `.log`, `.json`, `.csv`, `.pdf`, `.docx`) с автоматическим извлечением кодов ошибок и метрик телеметрии ([`diagnostics/document_service.py`](file:///d:/GDrive/Документы/Visual%20Studio%202022/ExpertSystem_auto_diag/diagnostics/document_service.py)).
4. **Голосовой ввод ([`diagnostics/voice_service.py`](file:///d:/GDrive/Документы/Visual%20Studio%202022/ExpertSystem_auto_diag/diagnostics/voice_service.py))**: поддерживает передачу аудиопотока и локальное распознавание речи через стек **GGML Whisper** (`pywhispercpp` / `whisper.cpp` / `faster-whisper`).

## 10. Режим для AR-очков типа RayNeo (`/ar/`)

По нажатию кнопки **«AR RayNeo HUD»** в шапке сайта (или при переходе по адресу `/ar/` либо `/?mode=ar`) активируется специализированный интерфейс дополненной реальности для очков типа **RayNeo Air / X2**:
- **100% оптическая прозрачность фона**: основной фон страницы принудительно заливается чисто черным цветом (`#000000`), который на MicroOLED дисплеях AR-очков при открытии на полный экран (`Fullscreen API`) остается полностью прозрачным.
- **Два свободно перетаскиваемых плавающих окна**:
  1. **`[AR ОКНО 1] КАМЕРА И ВИЗИР УЗЛА`**: живой поток камеры с прицелом диагностики, кнопкой мгновенного снимка узла в ИИ и голосовым вводом.
  2. **`[AR ОКНО 2] ОТВЕТЫ ИИ И ЧЕКЛИСТ РЕМОНТА`**: текущий диагноз, интерактивные чекбоксы шагов ремонта и инвентаря, а также поле быстрого вопроса.
- Оба окна поддерживают плавное перетаскивание (`Pointer Events` — мышью, тачскрином смартфона или трекпадом/кольцом AR-очков) и кнопку сброса расположения окон.

## 12. Запуск в Docker и Docker Compose

Проект полностью контейнеризирован с поддержкой GPU/Vulkan и автономного движка AirLLM:

```bash
# 1. Предварительно скачайте и нарежьте модель в локальную папку ./models (или контейнер сделает это при старте)
python prepare_airllm_model.py

# 2. Соберите и запустите контейнер
docker compose up --build -d
```

- Веса модели и послойные шарды AirLLM монтируются из относительной директории `./models:/app/models`, поэтому они сохраняются на хосте между перезапусками контейнера.
- Веб-интерфейс будет доступен на `http://localhost:8000/`, а AR-режим на `http://localhost:8000/ar/`.

## 14. Справочник REST API и тестирование

| Метод | Эндпоинт | Назначение |
|---|---|---|
| `GET` | `/` | Главный адаптивный интерфейс (Mobile-First PWA + Desktop) |

| `GET/POST` | `/api/settings/` | Получение и сохранение настроек AirLLM, GPU VRAM, окна контекста и голоса |
