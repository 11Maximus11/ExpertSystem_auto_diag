# Android shell

Generated by `lecodes app init android`. Daily workflow:

```
lecodes app sync                 # embed the compiled bundle + plugins into this shell
lecodes app open android         # open in Android Studio
lecodes app keystore create      # once: the release signing key (or `keystore use <file>`)
lecodes app build android        # signed release .apk + .aab → ../dist/
```

## Ownership

| Path | Owner |
| --- | --- |
| `app/` (sources, manifest, res, build.gradle.kts, proguard-rules.pro) | **Yours** after init — sync never rewrites them (it only restamps the `versionName`/`versionCode` and `isMinifyEnabled`/`isShrinkResources` values, manages `// lecodes:plugin`-tagged lines in the plugins block, and — when `app.json` sets `"icon"` — the icon files below) |
| `app/src/main/assets/` | CLI-owned — wiped and regenerated by every sync (the compiled `app.js` + its `// preload:` assets) |
| `res/mipmap-*/ic_launcher*`, `res/values/lecodes_icon.xml` | CLI-owned **only when** `app.json` sets `"icon"` — regenerated by every sync (plus a value-only `android:icon` restamp in the manifest); without the key sync never touches icons |
| `app/src/main/res/values/themes.xml` | **Yours** — its `Theme.LeCodesApp` must keep `parent="Theme.LeCodesRuntime"` (the window setup and the splash, see "Splash screen") |
| `settings.gradle.kts`, `build.gradle.kts` (root), `gradle.properties`, `lecodes-runtime/`, `plugins/` | CLI-owned — regenerated by every sync (`lecodes-runtime/src/main/res/`: `Theme.LeCodesRuntime` and, when `app.json` sets `"splash"`, the splash resources; with `"privacyPolicy"`, `lecodes_privacy.xml` — the policy URL a plugin's screen opens) |
| `gradle/`, `gradlew`, `gradlew.bat` | Written once at init |

## The SDK

`lecodes-runtime/build.gradle.kts` pins the exact `io.letary:lecodes-sdk` release, resolved
from the GitHub Releases of `letary/lecodes-android-sdk` through the ivy repository declared
in `settings.gradle.kts`. `lecodes app update` moves the pin (or set `app.json`
`android.sdk`). The SDK AAR ships no POM, so its own dependencies are declared explicitly in
the generated runtime build file.

## SDK variant

Sync links the smallest SDK artifact covering the engines the compiled bundle actually uses —
`lecodes-sdk` (full: 3D+2D), `lecodes-sdk-3d`, `lecodes-sdk-2d` or `lecodes-sdk-core`
(UI only) — so an app without 3D scenes doesn't ship Filament. If the project starts using an
engine, sync switches automatically on the next run; set `android.variant` in `../app.json`
to force one (needs lecodes-android-sdk >= 1.3.0; older releases ship only the full AAR).

Physics, navigation meshes and multiplayer ship in `lecodes-sdk` (full) ONLY —
`lecodes-sdk-3d` is 3D rendering without the game stack. Auto-selection reads which RENDERING
engines the bundle uses and cannot see those, so a project using `Physics`,
`CharacterController`, `NavMesh` or networking must set `android.variant: "full"` in
`../app.json` — otherwise those aspects silently do nothing on device.

`android.variant: "vulkan"` links `lecodes-sdk-vulkan`: the full engine set with Filament on
Vulkan (OpenGL ES where the device has no Vulkan 1.1), `arm64-v8a` only — for 3D games. Never
auto-selected; needs lecodes-android-sdk >= 2.2.11.

## App-local native code

Drop Kotlin files into `app/src/main/java/` and register them in `MainActivity` after the
`LeCodesRuntime.registerBundledPlugins(...)` call — `engine.registerCallback` for sync
globals, `engine.registerService`/`registerView` for channels (see the SDK docs). Add any
dependencies they need to `app/build.gradle.kts` — that file is yours.

## Release signing

The key lives in the project's `.env` (next to `app.json`; the CLI loads it for every command
and never pushes it):

```
LECODES_ANDROID_KEYSTORE_FILE=./android/release.keystore    # ./ = the project root; ~/ and absolute paths work too
LECODES_ANDROID_KEYSTORE_PASSWORD=…
LECODES_ANDROID_KEY_ALIAS=upload
LECODES_ANDROID_KEY_PASSWORD=…
```

`lecodes app keystore create` makes a new key and writes those lines; `lecodes app keystore use
<file>` attaches an existing one (a keystore outside the project is just a path); `lecodes app
keystore info` prints the SHA-1 / SHA-256 fingerprints the Play Console, Firebase and Google
Sign-In ask for. The same four names work as real environment variables (CI). Building from
Android Studio without the CLI? `android/keystore.properties` (gitignored, `storeFile` /
`storePassword` / `keyAlias` / `keyPassword`) is still honoured and wins over the env.
Never put passwords in app.json — `android.signing` there is metadata only.

With Play App Signing (the default for new Play apps) this key is the UPLOAD key — Google holds
the app signing key and a lost upload key can be reset through Play support. Without it, losing
the keystore means the app can never be updated. Back it up either way.

## Building

`lecodes app build android` syncs, runs `gradlew assembleRelease bundleRelease` and copies the
results to `../dist/<name>-<version>-<versionCode>.apk|.aab` (`-o <dir>` elsewhere). A release
without a signing key is refused (`--allow-unsigned` for a throwaway build); `--configuration
Debug` signs with the debug keystore. `--apk` / `--aab` pick one artifact.

Release builds run R8 (`isMinifyEnabled` + `isShrinkResources`): the SDK AAR ships the keep
rules its JNI bindings need, plugins ship theirs, `app/proguard-rules.pro` is for your own
classes. `app.json` `"android": { "minify": false }` turns it off (sync restamps the values).
R8 only touches the dex — the engine's native libraries and `app.js` are not shrunk.

`abiFilters` in `app/build.gradle.kts` keeps the package to the two ABIs the SDK ships
(arm64-v8a, armeabi-v7a).

## Icons

The easy path: set `app.json` `"icon"` to a square ≥1024px PNG/JPEG in the project (e.g.
`"icon": "icon.png"`, optional `"iconBackground": "#RRGGBB"` (any opaque CSS color) — the adaptive-icon
backdrop, default white). Every `lecodes app sync` then renders the full launcher set: legacy density
PNGs, the API 26+ adaptive icon (your image at 72dp on the 108dp canvas), and an Android 13
themed-icon (monochrome) layer that reuses the foreground silhouette.

Prefer hand-made icons? Leave `"icon"` unset and use Android Studio (right-click `res` →
New → Image Asset) — sync never touches icon files then. `drawable/ic_launcher.xml` is only
the init-time placeholder.

## Splash screen

`"splash": { "background": "#RRGGBB", "image": "./splash.png", "size": 160 }` in `../app.json`
(every key optional) makes every sync render the splash into `lecodes-runtime/src/main/res/`: the
colour (`background`, default `"iconBackground"`, default white) with the image fitted centred into
a `size`×`size` dp square (160 by default) — never at its pixel size — from
`drawable-mdpi…xxxhdpi/lecodes_splash.png` (size × 1/1.5/2/3/4 px: 160…640 at the default) of the one
master. Android 12+ shows it as the system splash (`windowSplashScreenBackground` +
`windowSplashScreenAnimatedIcon`: the image on the 288 dp icon canvas, inset (288 − size) / 2 on
each side as a fraction of the canvas — the system draws the icon small and scales it up, so a dp
inset would leave a dot — of which the system shows only the inner 192 dp circle — keep the mark inside one; a `size` above
192 is cut there, sync warns, and 288 is the most it takes), API 23–30 as the window background. Use
a square mark of at least 3 × size px (a non-square one is fitted into the square, a smaller one is
upscaled). No image = the colour
alone (and no icon on Android 12+, not the launcher one). The app holds the splash until its first
frame — through the first-launch wait of an OTA shell too. A bundle keeps it up past its start with
`app.splash.hold()` / `app.splash.hide()` (until its first screen has its data; 5 s at most).

### Animate the image

`"animation"` inside `"splash"` moves the image while the launch screen is up:

```json
"splash": {
  "background": "#FC2319", "image": "./splash.png", "size": 120,
  "animation": {
    "keyframes": [
      { "at": 0,    "scale": 0 },
      { "at": 400,  "scale": 1.2, "easing": "ease-out" },
      { "at": 1000, "scale": 1 }
    ],
    "fadeOut": 200
  }
}
```

Keyframes are like CSS ones: `at` is the time in ms (the first is 0, each later than the one
before; the last is the length of the animation), and any of `scale` (1 = `size`), `opacity`
(0…1), `rotate` (degrees), `x` / `y` (dp from the centre). A property moves between the
keyframes that name it and holds before the first and after the last. `easing` is the curve of
the segment that STARTS at the keyframe: `linear` (the default), `ease`, `ease-in`,
`ease-out`, `ease-in-out`, or the four numbers of a cubic-bezier (`[0.75, 0, 0.67, 1]`).
`fadeOut` is how long the launch screen fades away over the app, in ms (200 by default).

The system draws the launch screen before any code of the app runs, so it is a still picture —
the first keyframe. Start with `scale: 0` or `opacity: 0` and the system shows the colour
alone, the image growing or fading in from there; otherwise start from the image at rest
(scale 1, opacity 1, no rotation or offset), or it jumps when the animation begins — sync warns.
The animation plays once and the launch screen stays for that whole pass at least, the app
starting under it; an app that holds the launch screen (`app.splash.hold()`) keeps the image
at its last keyframe until it lets go. There is no loop.
On Android the system's splash cannot move a picture, so the animation is played by a view of the
app's own laid over the window with the same picture (`res/raw/lecodes_splash_animation.json`
in `lecodes-runtime`, CLI-owned); on Android 12+ the system's own exit animation is skipped
then, so the hand-over is a cut between two identical pictures.

It reaches the app through the theme: `Theme.LeCodesApp` in `app/src/main/res/values/themes.xml`
(yours) must say `parent="Theme.LeCodesRuntime"` and set no `android:windowBackground` of its
own. A shell generated before the key existed does not — `lecodes app sync` and `lecodes app
doctor` print the edit. Without the key the runtime theme keeps the black window shells always had.

## Notes


## Over-the-air updates

Native, before the JS engine: `LeCodesShell.boot(engine, activity)` in `AppViewModel` takes the
newest LOCAL bundle, then asks the source for newer code (a conditional GET; offline is a no-op)
and stores it. The FIRST launch of an installed binary waits for that answer (5 s at most, the
splash held on screen) and runs the newest bundle at once, so a fresh install from the store never
starts on the older code it shipped with; every later launch runs the local bundle at once and a
download applies on the NEXT launch. Configured in `../app.json`: `"update": true` = the
project's live bundle on the platform (a pushed project), `"update": { "url": "https://…/app.js" }`
= your own hosting, `false` = off. Sync writes the URL into
`lecodes-runtime/src/main/AndroidManifest.xml` (meta-data `io.letary.lecodes.UPDATE_URL`). A
download runs only when it is of this shell's SDK major and not older than the bundle running. A
store update keeps a downloaded bundle only when it is newer code than the one the update ships
(by compile date); otherwise the store build wins. A shell generated before OTA existed reads
`assets/app.js` itself, and one generated before the first-launch wait calls
`LeCodesShell.boot(engine, getApplication<Application>())` (which never waits) — replace either
with:

```kotlin
if (!LeCodesShell.boot(engine, activity)) Log.e("LeCodes", "bundled app.js is missing — run `lecodes app sync`")
```
- Push: the notification service needs `app/google-services.json` from the le.codes Firebase
  project; `lecodes app sync` applies the google-services Gradle plugin only when that file
  exists (and warns otherwise).
